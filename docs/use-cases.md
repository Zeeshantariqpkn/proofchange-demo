# ProofChange Use Cases

Three scenarios where ProofChange provides concrete value to engineering and
compliance teams.

---

## Scenario 1 — The Friday afternoon deploy

A backend team is shipping an urgent fix for a permissions regression. The
developer adds a new authorization branch — something like
`if role == "admin": return restricted_view()` — inside a function that
already has three tests. CI runs, all three pass, and the PR is approved.
Nobody has noticed that the new branch is entirely untested.

This is exactly the class of problem CI cannot catch. CI only verifies that
the *existing* tests pass. It has no awareness of which execution paths were
introduced by the diff.

ProofChange closes the gap at the diff level. [`engine/code_analyzer.py`](../engine/code_analyzer.py)
parses the changed function with Python AST and extracts every branch
introduced by the change — not as a regex heuristic, but as a structured
`BranchInfo` record with its expression and line number. [`engine/gap_detector.py`](../engine/gap_detector.py)
then cross-references those inferred scenarios against the existing test
suite. When no test name or docstring matches the new branch expression, the
detector emits a `TestGap` with `id: "GAP-001"`, `severity: "high"` (the
`_HIGH_SEVERITY_KEYWORDS` list promotes any branch involving `role`, `auth`,
`permission`, `token`, or `admin`), and a `suggested_test` name the developer
can act on immediately.

The evidence level in the resulting `EvidencePackage` drops to `"PARTIAL"` or
`"INSUFFICIENT"`, which blocks the GitHub Check Run from passing. The developer
sees the gap before the deploy, not after the incident.

The entire detection happens inside the normal PR review cycle. No separate
process, no manual audit step, no post-deploy forensics.

## Scenario 2 — The inherited legacy service

A developer joins a team maintaining a five-year-old service. Their task
is straightforward: update a single pricing function. They open
[`demo_repo/src/pricing.py`](../demo_repo/src/pricing.py), add a new
`customer_type == "vip"` branch, run the existing tests locally — green — and
open a PR.

What they do not know is that `calculate_discount` is called by three other
modules, that an unrelated batch-job test depends on its return value for the
`"premium"` path, and that nobody has written an explicit test for the
`"vip"` path because it did not exist until now.

ProofChange's [`engine/impact_analyzer.py`](../engine/impact_analyzer.py)
maps the affected function to its test coverage and classifies it as
`partial_paths` — a mapped test exists for `"premium"`, but the new `"vip"`
branch has no corresponding coverage. [`engine/gap_detector.py`](../engine/gap_detector.py)
emits `GAP-001` targeting the `"vip"` scenario specifically. The developer
does not need to trace the call graph manually; the gap record includes a
`suggested_test` name and [`ai/test_generator.py`](../ai/test_generator.py)
generates a runnable pytest scaffold targeting that gap, stamped
`# Generated by ProofChange — Bob-assisted workflow` so its origin is always
traceable.

Once the generated test is executed by the pipeline runner and passes,
[`engine/impact_analyzer.py`](../engine/impact_analyzer.py) reclassifies the
path from `partial` to `verified` — the `effectively_addressed_gap_ids` guard
confirms the gap was addressed by a test that actually ran and passed.
[`engine/evidence.py`](../engine/evidence.py) then assembles a `Change
Evidence Package` capturing the full record: diff, AST analysis, test map,
detected gaps, generated tests, execution results, and a final evidence level
of `"STRONG"`.

The developer attaches the `EvidencePackage` JSON to the PR. Their reviewer
gets a structured artifact rather than a verbal assurance that things were
tested. A developer who has never seen this service can confidently ship a
change on their first week.

## Scenario 3 — The audit trail

A compliance team needs to demonstrate to an auditor that every production
change in the last quarter was adequately verified before deployment. In a
typical team, this means interrupting engineers to write retrospective reports,
or hoping that PR comments contain enough information to reconstruct intent.

ProofChange produces a machine-readable `EvidencePackage` as a standard output
of every analysis run, whether triggered manually through the Streamlit
interface or automatically via the GitHub webhook in
[`github/webhook.py`](../github/webhook.py). Every package carries a stable
`id`, a `created_at` timestamp, the `repository` and `commit` SHA, the
`pr_number`, and a structured `evidence` block containing a `level`
(`"INSUFFICIENT"` / `"PARTIAL"` / `"STRONG"`) and a `rationale` string that
explains in plain language exactly why that level was assigned.

The `testing` block records `existing_tests`, `test_gaps` (each a `TestGap`
with its `id`, `function`, `scenario`, `severity`, and `reason`), and
`generated_tests` (each a `GeneratedTest` with its `targets_gap` reference
and `source` field distinguishing `"bob-assisted"` from `"runtime_llm"`
generation). The `execution` block records `tests_executed`, `passed`,
`failed`, `skipped`, and `duration_s`. The `paths` block classifies every
affected function as `verified`, `partial`, or `unresolved`.

[`engine/evidence.py`](../engine/evidence.py) can serialize any package to
Markdown via `to_markdown()` or persist it to disk via `save_package()`.
Because the format is consistent across every run, the compliance team can
query the archive directly — filtering on `evidence.level`, joining on
`commit`, or scanning `test_gaps` for any unresolved `"high"` severity items —
without asking engineers to produce anything new.

The audit trail is a byproduct of the normal development workflow, not a
separate compliance artifact that has to be authored after the fact.
